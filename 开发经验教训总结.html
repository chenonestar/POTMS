一、这个项目是什么形状的

先说清背景。下面所有的经验都由这个形状决定，换个形状未必适用。

一个 500 人规模、单用户、内网离线的政务系统：人员备案、证照登记、出国申请、证件领用、撤控备案。业务本身不复杂，复杂的是凭证的严肃性——领用单上有本人手写签名，撤控单要报送上级，这些纸面上的东西一旦开出去就不能被系统悄悄改写。

技术上做了一个不寻常的选择：同一套需求写了五遍（Python / Go / Rust / .NET / Java），五个实现共享同一个 data.db，界面渲染结果保持一致。这个决定的收益与代价，第八节专门谈。

阶段时间做了什么
Python 版成型7月上旬首版 + 运行反馈整改 + 分页/导出修正
四版铺开7月中 – 8月上旬Go → Rust → .NET → Java，逐个补齐，期间反过来修 Python 版的问题
五版对齐8月中下旬经办人真名 / 签名开关 / 界面一致性 / CI 与发布流水线
第 0 批8-26修 Go / Rust 的逾期分支（详见第五节，最惊险的一次）
第 1–3 批8-26 – 8-27把 Python 已定的业务规则同步到四版
第 4–6 批8-28 – 8-29Python 版跨表引用守卫、配置表改名同步、界面语义收口
一句话概括这两个月：前半程在「把功能做出来」，后半程在「把已经做出来的东西做对」。后半程发现的问题，几乎全都不是「功能缺失」，而是「功能都在，但改一张表悄悄改变了另一张表的含义」。这类问题不会报错，只会在半年后让人对着一条查不到的记录发愣。

二、为什么一个不复杂的系统改了这么多版

这是复盘时最该问的一句。前期做了需求分析，业务也不算复杂，为什么还是一轮接一轮地改？

下面的结论不是感想，是把 开发需求文档.html（1104 行）逐节对着返工记录查出来的。 先说结论：问题不在「分析得不够细」，而在「分析的维度不对」。

2.1 需求写得其实很细，但细在一个维度上

文档目录是 3. 人员备案 / 4. 证照登记 / 5. 出国申请 / 6. 撤控 / 7. 通用功能， 每个模块下面是字段表：字段名、数据类型、必填、说明。细到什么程度——逾期口径这一段：

正常行程为实际回国日期起 10 个工作日内（实际回国日期留空时以计划出行结束日计）； 取消行程为取消日期起 5 个工作日内。到期日当天仍算未逾期，次一日起计逾期。

连「当天算不算」都定了。这一层几乎没有返工过。问题全在别处。

2.2 三处返工的根，直接就写在需求文档里

① 文档自己前后不自洽：写了两条路径，只给一条定义了口径

5.1 申请流程分支明确写了两条路：

✅ 路径A：已有证件 → 办理证件领用手续（系统中记录领用）
📌 路径B：无有效证件 → 凭函向公安机关申办证件

而 7.6 逾期判据只写了一句：「已领用证件（证件领用日期非空）且尚未归还」。

路径B 根本没有领用记录，这条判据对它恒不成立——那批人整个掉出了逾期告警， 偏偏他们风险最高：证从公安办出来就一直在本人手上，单位连见都没见过。 第 2 批补「路径B 逾期」、第 0 批那个从没执行过的分支，根都在这里。

② 给了标签，没定义单位

7.7 首页仪表盘 REQ-010 原文：

证照状态总览卡片（在库 / 领用中 / 逾期未还，点击可跳转明细列表）。
备案人员总数及分类统计（按单位、政治面貌、职级等维度）。

第一句就是最后一轮返工那三张卡的出处。它给了标签，没说单位是「本」还是「条」； 还说「点击可跳转明细列表」，而明细列表是按出国申请组织的—— 于是实现顺着链接的方向按申请去数，标签却写着「证照」。 歧义是需求埋下的，不是实现跑偏。后果就是那组自相矛盾的数字：逾期比领用中还大。

第二句是那三个从第一版起就没渲染过的分布统计查询的出处——需求写了， 后端算了，前端没做，两个月没人发现。

③ 列了字段，没写字段背后的业务前提

6.1 撤控备案表列了 15 个字段，其中一行：

证件移交日期　DATE　选填　撤控后证件移交出去的日期

字段在，可「撤控以证件收缴完毕为前提」这条规则不在——第 4 批才补上，并改成必填。 整节唯一一句「数据一致性」只说「标记为已撤控，保留历史痕迹」， 关于撤控之后这个人名下的证件、出行、告警怎么办，一个字没有——那是第 5 批 B1 整批的内容。 撤销撤控更是完全没提。

2.3 诊断：文档回答了「有什么」，没回答「怎么变」

层次文档覆盖度返工量
字段级
类型 / 必填 / 格式 / 校验		 很全几乎为零
模块内规则
逾期天数、签名要求		 大部分少，集中在「写漏的分支」（路径B）
模块之间的关系
改 A 影响 B		 几乎全空第 4、5、6 批全部
状态迁移与回退
撤错了怎么办		 全空第 5 批 B2（撤销撤控）
统计口径
单位、集合关系		 只有标签仪表盘那一整轮

根因是文档的组织方式：按模块、按表单写。打开一张表单，能把它的字段列全； 但「改了这张表，谁跟着变」这个问题在任何一张表单里都看不见—— 它活在表单与表单之间的空隙里。目录结构本身就决定了这些空隙不会被覆盖。

同理，文档回答的是「正常情况下怎么用」。撤控撤错了、证照录重了、申请删错了、 人改名了——第 4/5/6 批的全部内容都是「出错了怎么办」，文档一句没提。

2.4 但有几笔账要算在实现头上，不能都推给需求

  • 三个死查询：需求确实写了「分类统计」，但算了不渲染、从第一版起如此、 两个月没人发现——这是实现没做完 加上 没自检。
  • 「逾期 3 > 领用中 2」：需求没定义单位是真的，但这个数字组合 摆在页面上就是明显不对。修 Go / Rust 逾期分支那阵天天开着这个页面，没看出来。
  • 提示指了一条走不通的路（「请先作废相关领用记录」，而判据根本不看 status）： 需求管不着，纯粹是写的时候没把自己的话在脑子里走一遍。

还有一条更要紧的：最后几轮最关键的发现，全是使用者追问出来的，不是测试、也不是自查。 「两个卡片重复吗」→「单位是不是按本」→「新办未入库算逾期吗」，一层比一层深。 测试守的是「我以为的规则」；我没想到的规则，测试也不会替我想到—— 测试防回归，不防「想漏了」。

2.5 那该怎么做

结论不是「需求分析要做得更细」，而是要多加四个维度。 成本不高，加起来大约半天：

  1. 画一遍状态机。证件有几种状态（在库 / 借出未还 / 新办未入库 / 已移交）， 人有几种状态（在控 / 已撤控），迁移由什么触发、有没有逆向边。 这一张图能一次暴露三件事：路径B 的状态没被覆盖、撤控没有逆向边、证件的计量单位是「本」—— 正好是第 2 批、第 5 批、仪表盘那轮返工的根。
  2. 做一张 CRUD 影响矩阵（表 × 增 / 删 / 改），每格填「影响哪些其他表」。 这一张表基本等于第 4/5/6 批的全部内容。
  3. 每个统计数字写明「单位 + 集合关系」。不写「在库 / 领用中 / 逾期未还」，写： 
    在库（本） + 借出未还（本） = 在控人员台账登记总本数
逾期 ⊆ 借出未还 + 新办未入库
    恒等式一旦写进需求，实现就跑不偏——最后那轮返工的成果，本质上就是补写了这两行。
  4. 每个不可逆操作预设回退路径。「撤控」这种把人从所有入口摘掉的操作， 设计时就该问「点错了怎么办」。

2.6 最该记住的一句：把返工分成两类

结构性返工——能避免

关系、状态、口径、回退。上面四条方法就是针对它的。这类返工是分析方法的欠账，不是必然。

意图性返工——只能用出来

「本月证件领用没什么用」「在库这个数我要拿去和柜子核对」「我要一份盘库清单」。 前期访谈问「首页要看什么」，回答多半是「要看统计」，问不出「我要拿它对柜子」。 这类返工是健康的，不该被当成失败。

这个项目真正的问题是：第一类被当成了第二类处理。 一直在「用出来 → 发现 → 修」的循环里，却始终没停下来做那张状态图和那个矩阵。 如果在第 4 批之前做一次，第 5 批、第 6 批和仪表盘那轮的内容会一次性浮出来， 而不是分四轮挤牙膏。

三、最有价值的一条实践：撤掉修复必须变红

如果这份总结只能留一条，留这条。

每写一条新测试，都要把对应的修复代码临时撤掉，确认这条测试真的会红；然后再把修复放回去。没做过这一步的测试，不算数。

这条纪律听上去像形式主义，但在本项目里它实打实抓出了 8 条「写了等于没写」的测试。这些测试全都是绿的，全都看起来在保护某个行为，而实际上把修复删光了它们照样绿：

用例为什么它是假绿怎么收紧的
Rust 逾期提示 只断言页面上有「应还」两个字。而 bug 恰恰是日期渲染成了空，「应还」还在 断言「应还」后面必须跟一个 8 位日期
Rust 申请选择页 断言某条申请不在页面上——可任何一个不含它的页面都能过，包括错误页 先断言「这确实是选择页」，再断言排除
证件号码只读 断言页面含 readonly。表单上别的字段本来就是只读的 收窄到 passport_no 那一个 input 标签内部
申请人锁定（第 4 批） 把申请人改挂到 2 号名下，但 2 号一本证都没有，先被「做证校验」挡下了。锁定即使完全失效，用例照样绿 同时把「是否做证」置为「是」，让锁定成为唯一的拦截原因
改名不联动（第 6 批） 用 updated_at 判断「没被改过」。这一栏只精确到秒，同一秒内的改动看不出差别，用例永远绿 改为断言「没有出现同步提示」且「没有写联动日志」
改名前有备份 断言备份目录非空。而取 CSRF 令牌走的就是首页，首页每天会自己备份一次——这条断言被日常备份糊弄了 先取令牌，再清空备份目录，之后出现的备份只可能来自强制备份
两次同步各留快照 两次改动用了不同的 tag，文件名天然不同。把「同名加序号」的防覆盖逻辑删掉，用例照样绿 另加一条直接针对防覆盖的单元测试：同一秒、同一 tag 连着调两次
.NET / Java 逾期 期望页面上有「应还」字样，但这两版是表格列渲染，本来就不会出现这两个字 改为匹配姓名后面的 8 位日期

连「验证实验」本身也会骗人

做回归验证时要先备份源文件、改坏、跑测试、再还原。有一次备份用了 cp，而不同目录下的文件基名相同，后一个盖掉了前一个；命令用 && 串联，前一步失败直接短路，于是「改坏源码」这一步压根没执行，测试跑的是原封不动的代码，得出了「撤掉修复测试仍然通过」的假结论——差点据此判定一条好测试是假绿。

做法：备份文件名带上来源目录；改坏之后先 grep 确认改动真的落进去了，再跑测试。验证手段本身也需要被验证。

为什么这条特别有效：一条测试有两种失败方式——「该红的时候没红」和「该绿的时候红了」。后者一跑就知道，前者永远不会有人告诉你。撤掉修复跑一次，是唯一能主动暴露前者的手段，成本大约 30 秒。

四、教训一：测试会骗自己

除了断言太松，还有几种更隐蔽的自欺。

4.1 静默失败比崩溃危险得多

同一个 bug（模板里用整数键去查字符串键的字典），在三个模板引擎上表现完全不同：

引擎表现发现难度
gonja（Go）抛错，整页 500立刻发现——只要有一个逾期的人，整个列表页打不开
minijinja（Rust）返回 undefined，静默渲染成空页面照常显示，只是日期没了。不看仔细根本发现不了
Jinja2 / Razor / JTE类型对得上，正常—

Rust 那种最麻烦：页面上是「应还: 」后面空着，看起来像是数据没填。第一版测试只断言「应还」两个字在不在，是绿的。

做法：断言要落在真正会变的那部分上，不是落在它周围的固定文字上。凡是「显示某个值」，就断言那个值的形状（8 位日期、非空数字），不要只断言标签。

4.2 「理应没问题」不算数

上面那个 bug，.NET 用 Dictionary<long,…>、Java 用 Map<Long,…> + getOrDefault，类型对得上，实测确实没问题。但还是给这两版补了用例。

理由很简单：今天「理应没问题」，是因为今天的类型恰好对得上。明天有人把 key 改成 String，这两版就会安静地退化成 Rust 那种表现，而没有任何东西会拦住他。

凡是「另外几个实现里出过的 bug」，即使本实现推理上不会中招，也要补一条钉住它的用例。用例守的是未来，不是现在。

4.3 幂等守卫是双刃剑

历史数据回填带了幂等守卫（「这条已经处理过就跳过」），这是对的——避免重复执行。但后来发现回填的推断逻辑本身写错了（把所有证件种类一律推定为护照）。

把推断逻辑改对之后，对已经回填过的库毫无作用：那些行已经被标记为「处理过」，永远不会再被碰。错的数据会一直躺在那里。

做法：修复一个「一次性数据处理」的逻辑时，必须同时问一句「已经被错误处理过的存量怎么办」。本项目的解法是另加一条订正迁移，判据卡死在「回填自己产的行」上（备注是那句原文、且没有签名），改完备注即自然失配，不需要版本表。

4.4 断言写对了，但造的数据分辨不出对错

这是比「断言太松」更隐蔽的一种。断言本身完全正确，是 fixture 里的数据凑巧让它失去了鉴别力——代码写错了，它照样绿。

首页四档证件去向有一条恒等式：逾期 ⊆ 借出未还 + 新办未入库。用例照着写了：

# 断言没毛病
assert 逾期 <= 借出未还 + 新办未入库

可当时 fixture 里只有两个「在外」的样本，两个都已经超期。于是实际数据是 逾期 2 ≤ 借出 1 + 新办 1 = 2——恰好取等号。这条断言在这组数据下， 代码把 ⊆ 实现成 = 也照样通过：只要把「新办未入库」不加时间条件地 一律当成逾期，数字仍是 2 ≤ 2。补一个「做证批下来、下个月才出发」的样本（在外，但还没到期）之后， 变成 2 ≤ 3 的真子集，那种错法立刻转红。

回头看，前面表里有两条其实是同一个病：

  • 申请人锁定——换人的目标对象「一本证都没有」，于是先被另一条校验挡下。 锁定完全失效也测不出来。少的是「目标对象持有证件」这个样本属性。
  • 两次同步各留快照——两次改动用了不同的 tag，文件名天然不撞， 「同名加序号」的防覆盖逻辑删掉也照样绿。少的是「同一秒、同一 tag」这个样本。
写完一条断言，接着问一句：「什么样的数据能让这条断言在代码错的时候仍然通过？」 如果答得出来，而 fixture 恰好就是那种数据，就补一个反例样本进去。 尤其是 ⊆ / ≤ / 「A 是 B 的子集」这类关系——必须造出严格小于的情形， 取等号的数据检验不了子集关系。

还有一层值得记下：本项目里这类问题没有一次是测试自己发现的， 全都是有人追问「这个数到底怎么算的」时才浮出来。「撤掉修复必须变红」能抓住断言太松， 但抓不住样本不足——因为撤掉修复之后，那组数据仍然产不出差异。 补的办法是撤修复时刻意往错的方向改（比如把「超期才算逾期」改成「没入库就算逾期」）， 而不只是把修复整段删掉：删掉往往退回一个明显崩坏的状态，反而容易红； 改成一个「看起来也说得通的错法」，才真的在考验用例。

五、教训二：时间与环境的隐式依赖

这一类 bug 的共同点是：代码没变，某一天突然就红了 / 或者本地永远绿、CI 永远红。

5.1 按日历引爆的定时炸弹

某天例行跑基线，Go 版测试红了一条，而那个目录几周没人动过。查下来是这样：

# 测试里写死的造数
出行结束日期      20260811   （未归还）
应还到期日 = 结束 + 10 个工作日 = 20260825

# 于是
上次 CI 绿的日子   20260822 → 未逾期 → 「逾期提示」这个分支从来没被执行过
今天             20260826 → 已逾期 → 分支第一次执行 → 炸

也就是说，Go 版的「证件逾期未还」提示块从上线起就没工作过——只要真实数据里出现一个逾期的人，整个出国明细列表就是 500。测试「覆盖」了这段代码，但那个分支一次都没走进去过，覆盖率是假的。

测试造数一律用相对今天的日期（今天 - 90 天），不写死具体日期。写死的日期会让某个分支「今天走不到、明天才走到」，而你不知道是哪天。

顺带一提：这也说明定期无改动地跑一遍全量 CI 是有价值的。这个 bug 不是被某次提交触发的，是被日历触发的。

5.2 同一个编码问题，咬了两次

这是整份总结里最值得记住的一条，因为它说明「修好一个 bug」和「消除这一类 bug」是两回事。

时间位置现象
2026-08-22 产品代码
app.py		 打包成 exe 后，只要 stdout 不是控制台（重定向到文件、注册成服务、被别的进程接管管道），Python 就改按系统 ANSI 代码页编码。英文 Windows 是 cp1252，编不出启动横幅里的中文，print 直接抛异常，程序启动即崩——而且崩在写日志这件事上，日志里往往什么也留不下
2026-08-29 测试代码
test_hardening.py		 一条测试用 Path.write_text("不是备份文件…") 造干扰文件，没给 encoding=。本地 Linux 默认 UTF-8，写得出来；CI 的 Windows 运行器默认 cp1252，UnicodeEncodeError，216 条测试红 1 条，整条流水线挂掉，包也没打成

第一次修得相当彻底：在第一次 print 之前把 stdout/stderr 定死为 UTF-8，还配了一条真的让子进程带 PYTHONIOENCODING=cp1252 去跑的回归测试（不是模拟，是让解释器真的换编码器）。但修复的范围只到那一个调用点。「这台机器的默认编码可能不是 UTF-8」这个认识，没有被推广成一条覆盖全仓的规矩，一周后就在测试代码里复发。

修完一个 bug，紧接着做一次同类扫描：这个根因还能在哪里成立？本项目补做这次扫描只花了一条 grep（全仓 write_text / read_text / open() 缺 encoding=），结果是产品代码干净、只有那一处漏网。这条 grep 早一周跑，就不会有第二次。

更一般的结论：开发环境（Linux/UTF-8）和目标环境（Windows/ANSI 代码页）不一致时，差异只会在 CI 或客户现场暴露。这类差异要么在本地能复现（本项目就是用 encoding="cp1252" 当场复现确认的，不靠猜），要么就得靠 CI 兜——不能靠「我这儿是好的」。

5.3 进程级状态会让测试互相污染

.NET 版的数据目录用环境变量 POTMS_BASE 指定，而环境变量是进程级的。并行跑的测试互相改这个变量，结果是随机失败。解法是把相关测试放进同一个 xUnit Collection 强制串行。

同类的还有：Python 版备份模块用了一个「今天已检查过」的进程内全局标记，跨测试残留，导致某些用例的前置条件依赖执行顺序。

做法：任何进程级/模块级的可变状态（环境变量、全局标记、单例缓存），在测试里都要么显式重置，要么串行化。

六、教训三：冗余字段有两副面孔

这是本项目最有普适价值的一条设计经验，也是第 4–6 批几乎全部工作的根源。

系统里大量业务表冗余存了人员信息（姓名、单位、部门）和配置项文字（政治面貌、报送单位名称）。这些冗余不是设计失误，但它们分成语义完全相反的两类，而代码一开始没有区分这两类——这才是问题所在。

台账：应当跟着人走

certificates（证照台账）记的是「这个人现在手上有哪几本证」。人改了名、调了单位，台账必须跟着改。

不跟着改的后果：这本证在旧名下消失、也不在新名下，按姓名搜、按单位筛两边都找不着。

单据：应当就地定格

cert_issuance / travel_details / decontrol_filing 是开出去的单子，上面印的是开单那天的信息，还带着本人手写签名。

跟着改的后果：那张签了字的凭证被事后改写，指向了另一个人——这正是签名要防的事。

每加一个冗余字段，都要在字段旁边的注释里写清它属于「台账」还是「单据」。同样是一列 name，两类的正确行为正好相反，光看字段名分辨不出来。

6.1 「按文字引用」的配置表是隐形雷区

三张配置表（组织架构 sys_org、数据字典 sys_dict、报送单位 sys_submit_unit）都不是被外键引用的——业务表里存的是当时那个名字的文字本身。于是配置表这一侧完全不知道自己被谁用着，两个洞：

  • 删除：把「技术部」从组织树上删掉，几百条历史记录里的「技术部」原地变成一个下拉里再也选不到的孤儿值——按部门筛选选不出来，导入校验也认不了。而删除操作原来是裸 DELETE，什么都不查。
  • 改名：新数据用新名、老数据用旧名，同一个部门在统计里裂成两个，两边都不全，而且没有任何报错。

更麻烦的是数据字典内部还要再分一层：存编码的类别（学历/学位/职称/职级，库里放 01/02，渲染时才翻成文字）改显示值是完全安全的；存文字的类别（政治面貌/出国类别等）改名就会让历史数据失联。同一个界面上的八个类别，一半安全一半危险，而原来的页面提示还写着「如需停用，可保留或修改显示值」——对存文字的那一半，这句话是在指一条会毁数据的路。

最终的处理口径（可以直接照搬）

  1. 删除：先统计被引用了多少条、被哪几张表引用，有人用就拒绝并报清楚，不给「强制删除」的口子。没人用的仍然要能删——守卫不能把清理这条路也堵死。
  2. 改名：有历史数据在用时，必须明确表态历史数据跟不跟着改，不能默默改一半。判据用「实际有多少条记录存着这几个字」，不用「这个类别标注为存文字」——存编码的列天然统计不到显示值，自然不会被问，而历史导入把文字直接写进这些列的情况也能兜住。
  3. 同步：属于批量重写历史，走「强制备份 + 一条说得清的操作日志」，备份文件名同时写进页面提示和日志，出事时知道拿哪个文件回退。
  4. 分不清就不动：组织树上有重名节点时中止同步——按文字分不出历史数据属于哪一个，一条 UPDATE 会把两边都扫走。宁可不同步，也不能改错别人的。
  5. 使用量前置显示：树上/列表上直接标出「在用 N 条」，让后果在动手之前就看得见，而不是点了删除才被弹回来。

6.2 备份策略：一天一份是不够的

最初「动历史数据前强制备份」复用的是每日备份（data_YYYYMMDD.db）。问题在于同一天做两次批量改动，第二次会把第一次改之前的那份盖掉——第一次改错了就再也退不回去，而这恰恰是留这份备份要防的事。

改法：改前快照独立成 before_<做什么>_YYYYMMDD_HHMMSS.db，精确到秒、从不覆盖（同一秒撞名再加序号），文件名里的 tag 说明是哪次改动，出事时不用逐个打开文件猜。

「保险」措施本身也要审一遍：它在最坏情况下真的还在吗？一份会被覆盖的备份，在「同一天连出两次错」这个最需要它的场景下，恰好是不在的。

七、教训四：界面与文案也是逻辑

这一类问题不会让程序出错，只会让用户做错事。危害不小于崩溃。

7.1 提示指了一条走不通的路

删除出国申请被挡住时，系统提示：「该出行记录已有 N 条证件领用记录，不能删除。如确需删除，请先作废相关领用记录。」

照着做没有用——判据是 SELECT COUNT(*) FROM cert_issuance WHERE travel_id = ?，不看 status，作废的照样算数。用户会作废掉一条本来好好的领用记录，然后发现还是删不掉。

而这不是判据写漏了：领用单上有本人手写签名，作废是「这次领用作废」，不是「这次领用没发生过」，单子仍要留档、仍然指着这条出行。判据是对的，错的是话。

改法：说清楚被什么挡住（按已领用未归还／已归还／已作废分别报数），并指出真正该走的路——这次没成行就用「取消行程」。

写一条拒绝提示时，把「按提示做一遍」在脑子里走完：做完之后真的能过吗？走不通的提示比不给提示更糟，它会消耗用户的信任，还会让他做出破坏性的操作。

7.2 办不了的事不该给入口

出国申请列表里「证件领用登记」按钮对每一行都亮着，点进去才被挡回来（行程已取消 / 已有未归还的记录）。

改法：按同一判据决定亮灭，灰掉时用 title 说明原因。关键是判据只写一次——抽成一个函数，列表按钮和领用模块的准入共用它，并专门写了一条测试盯住这个一致性。两套并行的判据迟早对不上，那时候列表说能办、点进去说不能办，比现在还糟。

7.3 拦截要发生在进表单之前

撤控备案有前置条件（证件必须已收缴）。第一版把校验放在提交时——让人填完一整张十几个字段的表再说不行，是最没必要的一种为难。改成在 GET 进入表单时就拦。

7.4 单向门

「撤控备案」会把一个人从所有在办入口里摘掉（发起撤控的下拉、出行申请的选人、首页告警都只认在控人员）。而界面上没有任何回头路——撤错了一个人，代价不是一条脏数据，是这个人的业务彻底办不了，只能去改库。

任何会改变实体状态、且改完之后该实体从多个入口消失的操作，都必须同时提供撤销入口。设计时问一句：「点错了怎么办？」如果答案是「去改数据库」，那这个功能没做完。

7.5 算了不用的代码，比没写更糟

首页的处理函数算了四份数据（三项分布统计 + 证照到期预警）传给模板，而模板从第一版起就没用过它们（git log -S 全历史查证）。每进一次首页白跑四个查询，其中一个还带 JOIN。

更要紧的是第四份：「证照到期预警」是唯一一个没做完的功能——数据算好了、扔掉了，用户在首页上看不到任何「谁的护照快到期了」的提示。它不是多余的代码，是做了一半的功能伪装成了多余的代码。

做法：模板上下文没有编译期检查，多传的变量永远不会报错。清理时不能只问「这个变量有没有被用」，还要问「它本来是打算做什么的」——本项目的结论是三份删掉、一份补上界面。

八、教训五：多实现并行的真实代价

五个语言写同一套需求，这个决定值不值？分开算账。

它确实做到的

  • 互为对照，能发现单版本发现不了的 bug。「逾期提示从没工作过」就是在五版横向比对时暴露的——单看 Go 版，它的测试是绿的。
  • 共享 data.db 强制了 schema 纪律。schema 只有一个源头（database.py），自动生成 .NET 的 Schema.cs 与 Java 的 schema.sql，CI 用 --check 守着。改一处忘了同步，CI 立刻红。
  • 「同一个 bug 在不同引擎上的不同表现」是极好的教材（见 4.1），它让「静默失败」这件事变得可见。

它真实的代价

  • 一处业务规则改动 × 5。第 1–3 批每批都要拆成上下半（Go/Rust 一批、.NET/Java 一批）才做得完。
  • 三个 Jinja 方言互不兼容。Jinja2 / gonja / minijinja 语义有差异（minijinja 还会把 url_for 的输出 HTML 转义，/ 变成 &#x2f;），模板不能直接复制。
  • 看起来一样的东西未必一样。在 JTE 模板里写成 Razor 的 @* *@ 注释语法，结果注释文字被当成页面内容渲染出来了——已签字的记录上凭空多出一行「更正证件种类」。
  • 数据变更会外溢。Python 版把某个字段置空写进共享库，另外四版立刻显示成空白。
  • 欠债会累积。截至本文，Python 版的第 4–6 批还没有同步到四版。
怎么判断：如果目标是「交付一个能用的系统」，五版是巨大的浪费——一个版本就够了，省下的力气够把测试和文档做得厚一倍。如果目标是「技术选型对照」或「同一套逻辑的交叉验证」，它做到了别的办法做不到的事。关键在于这个决定要在一开始就说清是为了什么，并且明确「哪一版是源头」——本项目定的是 Python 版为准，这一点定得早、执行得住，是它没有失控的主要原因。

九、成功经验：值得原样带走的做法

9.1 判据只写一次

本项目反复出现的一个模式：同一条业务判据在两个地方各写了一遍，然后慢慢漂移。

  • 出国明细列表的逾期红条高亮和「逾期未还」筛选原本各算一遍。加「已撤控人员不进告警」这条规则时，差点只加在筛选那一侧——那样页面会标红一个筛不出来的人。
  • 列表上的「领用登记」按钮该不该亮，和领用模块自己的准入判据。
  • 三处配置表的「谁在引用这几个字」，收进一个共用模块。
发现「两个地方在回答同一个问题」，立刻抽成一个函数，让两边都调它。哪怕看起来只是两行 SQL 的重复——重复的不是代码，是判断，判断重复了就一定会分岔。

9.2 注释写「为什么」，不写「做了什么」

这个项目里大量守卫逻辑，单看代码都像是多余的额外检查。代码里的注释统一解释业务后果而不是复述代码：

# 撤控表上「证件移交日期」这一栏本身就说明：业务上撤控是以证件收缴完毕为前提的。
# 但此前代码不查，于是可以「带证走人」——人撤控了，那条逾期告警还挂在首页，
# 而这个人已经不在管理范围内，谁也处理不掉，成了永远消不掉的死账。

效果：半年后（或者换个人）看到这段，不会把它当成可以顺手简化掉的冗余检查。测试的 docstring 同样这么写——一条测试的名字说它测什么，docstring 说不这么做会出什么事。

9.3 动历史数据前：强制备份 + 一条说得清的日志

凡是一次性改掉几百条历史记录的操作（改名同步、经办人回填、启动时的数据订正），统一走：

  1. 先存一份带时间戳的独立快照，备份失败就中止，不动数据；
  2. 写一条能说清「什么变成了什么、共几条、改前快照叫什么」的操作日志；
  3. 把快照文件名同时显示在页面提示里，用户当场就知道回退拿哪个文件。

而日常的单条联动只写日志、不备份——每改一次名就存一份数据库副本，备份目录会被淹掉，真出事时反而找不到有用的那一份。这条边界要划清楚。

9.4 分批推进，每批停下报告

后半程的工作节奏是固定的：先答疑 → 出计划 → 等审定 → 执行一批 → 停下报告 → 等审定 → 下一批。

几个具体的好处：每批的提交信息能写清「为什么这么改」（因为决策刚刚发生过）；发现问题时回退范围小；也避免了「一口气改二十处、审的人无从下手」。

配套的一条：凡是遇到需要拍板的分歧，先停下来问，不要替对方决定。例如「撤销撤控时那条记录是物理删除还是标记作废」——两种都说得通，但选错了要返工。

9.5 实机验证，不只跑测试

几个关键节点上，起真进程把完整流程走了一遍（不是跑测试，是真的点）。有一次这么做，发现验证脚本自己漏设了环境变量、连到了另一个空库——如果只看测试，这个假阴性会被当成实现有问题去查。

9.6 CI 只做该做的事

五版各有一条工作流，而 .NET / Java 的触发路径里都有 database.py（为了守 schema 同步）。结果只改 Python 版也会顺带重打两份一模一样的 Windows 包。

改法：校验与测试照跑（那是测试关切，不能省），打包按「本次改动有没有落到本版自己的目录」跳过。发版不受影响——发布流水线无论如何都把五版一起构建。

十、下一个项目的检查清单

把上面的经验压缩成可以逐条对照的动作。

时机检查项
设计每个冗余字段标注「台账（跟着源头变）」还是「单据（就地定格）」，写在字段旁边
设计凡是「业务表存配置项的文字」而非外键，配置表那一侧必须同时设计删除守卫与改名同步，不能等出事再补
设计每个改变状态的操作都问一句「点错了怎么办」，答案是「去改数据库」就说明没做完
设计同一条判据只允许有一个实现，两处需要就抽函数，不接受「就两行 SQL 抄一下」
编码所有文本 IO 显式给 encoding="utf-8"；开发机与目标机编码不一致时，本地要能复现目标环境
编码注释写业务后果，不复述代码。守卫类逻辑尤其要写清「不这么做会怎样」
编码批量改历史数据 = 强制备份（独立、带时间戳、不覆盖）+ 一条能说清改了什么的日志 + 页面告知备份文件名
测试每条新测试都撤掉修复跑一次，确认它会红。这一条不能省
测试断言落在会变的值上（日期的形状、数字），不要只断言周围的固定文字
测试造数用相对今天的日期，不写死；进程级状态显式重置或串行化
测试断言「不包含某人」时，先确认页面确实是那个页面、并且把范围截到那一块再断言
测试回归实验本身要验证：改坏之后先确认改动真的落进去了，再跑测试
测试写完断言问一句「什么样的数据能让它在代码错时仍然通过」；⊆/≤ 这类关系必须造出严格小于的样本，取等号检验不了子集
测试撤修复时往错的方向改，不只是整段删掉——删掉容易退回明显崩坏的状态，改成「看起来也说得通的错法」才真在考验用例
界面每条拒绝提示，把「按提示做一遍」在脑子里走完——走得通吗？
界面办不了的事不给入口；给了就得说清为什么灰
界面前置校验放在进表单之前，不让人填完再说不行
收尾修完一个 bug，立刻做一次同类扫描：这个根因还能在哪里成立？
收尾修一次性数据处理的逻辑时，同时问「已经被错误处理过的存量怎么办」
收尾改了业务口径就同步改需求文档——文档不改会悄悄地和实现对不上
收尾定期无改动地跑一遍全量 CI，接住「按日历引爆」那类问题

十一、这个项目还欠着的

总结如果只讲成绩就没用了。截至本文，以下事项确实还没做。

优先级欠账影响
高 第 4–6 批（跨表引用守卫、配置表改名同步、界面语义）只做了 Python 版，Go / Rust / .NET / Java 尚未同步 四版目前仍可能删掉被引用的证照、带证撤控。而五版共享同一个 data.db，从任何一版做出的破坏，其余四版都要承受
中 发布工作流 release.yml（425 行，五版一次出齐）从来没有真正跑过一次 真到发版那天才第一次跑，是最不该冒的险。应当先拿一个测试 tag 空跑一遍
中 仓库里没有约定文档（如 CLAUDE.md / CONTRIBUTING.md） 「Python 为源头」「schema 改了要重新生成两份」「新测试必须验证会红」这些规矩全靠口头传，换人就断
低 Go 与 Python 版没有版本号字符串 拿到一个 exe 无法判断是哪次构建的
低 系统内没有「从备份恢复」的界面入口（README 里写了三步手工恢复） 真出事时操作员要停服、找文件、改文件名，容易再出错
最后一条，也是最该记住的：这份清单里的第一项——「Python 改完了，四版还欠着」——正是「修好一个 bug 不等于消除这一类 bug」在项目层面的翻版。第五节讲的是同一个根因在一周内咬了两次，这里是同一个根因在四个实现里等着。改完一处，永远要接着问一句：还有哪里也是这样？
