第 0 部分　模板说明

0、怎么用这份文档

这份文档有两个身份，读的时候要分清：

  • 身份一：POTMS 现行口径的权威说明。正文写的全是这个系统此刻真实的样子——每一条状态迁移都对应一个真实存在的路由，每一处守卫都对应一个真实存在的函数，每一个统计数字都对应一个真实存在的判据函数和守着它的测试。
  • 身份二：下一个项目写需求分析的模板。每一章开头有一个可折叠的「▸ 这一节怎么填」，讲的是这一章存在的理由：它回答什么问题、不写会付出什么代价（都是本项目付过的）、以及怎么填。

换项目复用时：折叠块留下，正文全换。章节骨架是通用的，正文是 POTMS 专有的。

0.1 三条硬规矩

规矩一：写现状，不写理想。 文档里不出现「应当」「建议」「后续可以」。写不出现状的地方，说明那件事根本没做——那就写进第 15 章的欠账清单，而不是用一句「应当」把它糊过去。 本项目上一版需求文档正是死在这条上：它写着「证件移交日期 DATE 选填」，而代码里这一栏早已改成必填；写着仪表盘有「在库 / 领用中 / 逾期未还」三张卡，而实际是四档且单位全变了。读文档的人照着做，做出来的是一个不存在的系统。
规矩二：每一条规则都要能追回去。 状态机的每条边写清触发它的路由；矩阵的每个格子写清执行它的函数；每个统计数字写清算它的函数 + 它满足的恒等式 + 守着它的测试。追不回去的条目，要么是想当然，要么是已经腐烂了。
规矩三：判据只写一次。 同一个业务判断（「谁算逾期」「哪些申请还能开领用单」「一本证在不在库」）在系统里只能有一个函数，所有调用方共用。文档同理：判据的定义只在一处展开，别处一律引用，不复述。 这条是本项目返工次数最多的一条教训，详见《开发经验教训总结》第九节。

0.2 折叠批注的用法

每一章正文之前的折叠块统一是三段式：

段落写什么
回答什么问题这一章存在的唯一理由。答不上来的章节就该删——凑齐八股会让真正重要的内容被稀释。

1、项目概述与边界

这一节怎么填
回答什么问题
这个系统管到哪儿为止。不是「它能干什么」——那是功能清单，第 5 章才写；这里要的是那条线：线内的事必须做对，线外的事一件也不做。
不写的代价
没有「非目标」清单，每一次「顺手加个功能」都显得合理。本项目首页曾经计算「按单位 / 按政治面貌 / 按职级」三项分布统计并传给模板，而模板从第一次提交起就没有渲染过它们（用 git log -S 核实）——每进一次首页白跑三个查询，其中一个还带 JOIN。它不是被用坏的，是一开始就不该进来：500 人规模的分布统计是报表需求，不是每天看的告警。写清非目标，它在需求阶段就会被挡下。
怎么填
先写「目标」和「使用场景」，再逼自己写满至少 6 条「非目标」。非目标要写具体到会被误解的那种：「不做多用户」不够，要写「不做角色权限体系——users 表不含 role 列，所有登录者权限相同」，否则下一个人会理解成「暂时只有一个用户，将来加角色」，然后按可扩展的方式设计一遍。

1.1 目标

为一家单位的因私出国（境）证照保管处提供全流程台账：从人员备案、证照收缴登记，到出国（境）申请、证件领用与归还，直至人员撤控与证件移交，全部留痕、可查、可导出、可打印。

核心价值不是「审批」，而是把每一本证的去向说清楚——任何时刻都能回答：这本证现在在哪儿、在谁手上、该什么时候回来、有没有超期。

1.2 使用场景与规模假设

维度取值由此推出的设计决策
部署环境单位内网，完全离线前端不引任何 CDN，图表用内联 SVG，字体用系统字体栈；文档本身（含本文）也必须离线可看。
并发用户1 人（保管处经办人）不做角色权限、不做行级锁、不做乐观并发控制；SQLite 单文件足够。
数据规模在控人员 500 人量级，历史记录数千条列表页全量下发 + 前端按视口窗口化（list_all()），不做服务端分页；全表扫描的统计查询可以接受。
运行方式单机常驻，办公时间开着每日备份挂在首页访问上触发（run_daily_backup()），不依赖定时任务服务。
数据可靠性要求纸质单据为准，系统为台账关键单据（领用单）采集手写签名并可打印归档；系统数据可从 backup/ 恢复。

1.3 系统边界（在管范围内）

管什么到哪儿为止
人员备案登记 → 变更 → 撤控 → 撤销撤控。不管人事系统里的入职离职，备案是本系统自己的一份名册。
证照台账收缴入库登记（三类证件，一人一行三个号码槽）→ 号码变更（换发）→ 随撤控移交出库。
出国（境）申请申请登记 → 附件上传 → 行程取消 / 恢复 → 归档。不管审批流转本身：审批在线下走纸质，系统记的是审批结果与日期。
证件领用开领用单（手写签名）→ 归还登记（手写签名）→ 作废。唯一记录「这本证现在在谁手上」的地方。
逾期催还按工作日算到期日并在首页与列表告警。不管通知发送：没有短信、没有邮件、没有站内信，经办人自己看。
盘库出一张「此刻应当躺在柜子里的每一本证」的清单，供与实体核对。

1.4 非目标（明确不做）

不做什么为什么，以及别误解成什么
角色权限体系users 表只有 username / password_hash / full_name，没有 role 列。所有登录者权限完全相同。不要理解成「暂时只有一个用户，将来加角色」——按可扩展方式设计会凭空引入一层从不会被用到的判断。
审批工作流引擎不做多级审批、待办流转、会签。审批在线下，系统只记结果字段（审批日期、批号）。
与外部系统对接不对接人事系统、不对接公安出入境系统、不做接口。数据靠人工录入与 Excel 导入。
报表与分布统计首页只放要行动的告警。按单位 / 政治面貌 / 职级的分布统计已从代码中删除（它们曾计算而从未显示）。需要分布，走导出到 Excel 自己透视。
通知推送无短信、无邮件、无消息中心。逾期靠首页与列表页的告警区，经办人上班看得到。
移动端只保证桌面浏览器与打印。页面用 Bootstrap 5 所以在窄屏不会散架，但不为移动端做交互设计。
附件全文检索附件只存文件、分类、批次，按记录挂靠检索，不解析 PDF 内容。
系统内的备份还原入口备份自动做（每日 + 改前快照），还原是手工三步（停服务、换文件、启服务，见 README）。这是一笔已知欠账，不是遗漏——见第 9 章。

2、术语表

这一节怎么填
回答什么问题
同一个词，在这个项目里只许有一个意思。
不写的代价
本项目在「证照 / 证件」上吃过亏：菜单叫「证照台账」，卡片叫「证件在库」，导出叫「证件盘库清单」——同一批东西三个叫法，读界面的人要自己猜是不是一回事。更贵的是单位：仪表盘上一度同时摆着三个数，一个的单位是「人」，一个是「出国申请条数」，一个是「本」，摆在一行里看起来可以互相加减，实际上完全不同维度，于是出现了「逾期 3 > 领用中 2」这种逻辑上不可能的组合，一直发布到了首页。术语表不是给外人看的礼节性章节，它是单位一致性的第一道闸。
怎么填
三件事：①每个词一句定义；②凡是可数的，必须标注单位（人 / 本 / 条）；③写出「不是什么」——只有正面定义挡不住误用，「借出未还 ≠ 逾期」这种否定句才挡得住。

2.1 主体与单据

术语单位定义 / 不是什么
备案人员人纳入本单位因私出国（境）管理范围的人，表 personnel_filing。状态只有有效 active 与 已撤控 decontrolled 两种。
信息登记表条表 personnel_info，人员的基础信息（含部门）。一条信息可被多条备案引用，也可以没有备案引用（孤儿），有专门的清理入口。
证照台账条表 certificates，一人一行。不是一本证一行——一行里有三个号码槽。所以「证照登记 15 条」的意思是 15 个人有证，不是 15 本证。
号码槽本台账一行里的三组「号码 + 有效期 + 上交日期」字段，对应普通护照 / 往来港澳通行证 / 大陆居民往来台湾通行证（代码 certificate.CERT_SLOTS）。一个非空号码槽 = 一本证，所有「本」为单位的统计都以此为原子。
出国（境）申请条表 travel_details，一次出行一条。行程状态 normal / cancelled。
领用单条表 cert_issuance，凭出国申请从保管处借出证件的单据，带本人手写签名。状态 issued / returned / voided。一次申请一次只能借一本证。
撤控备案条表 decontrol_filing，上报「此人不再纳入本单位管理」的单据。不是一个状态标记——它是报出去的一张单，所以撤销时是物理删除（见 9.2）。

2.2 台账 vs 单据（本项目最贵的一对概念）

certificates、cert_issuance、travel_details、decontrol_filing 四张表里都有 name / unit / department 这几列，列名一样，正确行为相反：

类型哪些表人员改名 / 改单位时理由

单据cert_issuance

decontrol_filing		必须冻住（无任何同步） 单据是开出去的那张纸，上面印的是开单那天的姓名与单位。事后跟着人改，等于篡改历史凭证——尤其 cert_issuance 上有本人手写签名，改了签名就名不副实。

2.3 两条领证路径

路径证从哪儿来系统里的痕迹逾期判据
路径 A
领用		本人名下的证原本就收缴在保管处，出国时借出 有 cert_issuance 记录；travel_details.passport_collect_date 由领用单派生而非空 validators.is_cert_overdue：已领用 + 未归还 + 已过到期日
路径 B
做证		本人凭同意申办函自己去公安办新证，证从没进过保管处 没有领用记录；passport_collect_date 永远为空；need_new_passport='是' validators.is_new_cert_overdue：判据换成「新证号码有没有进证照台账」——进了台账等于已交回收缴（台账登记时上交日期必填）
为什么这一对必须写进术语表：路径 B 的人风险最高——那本证从办出来起一直在本人手上，单位连见都没见过。而最早只实现了路径 A 的判据，passport_collect_date 为空直接返回 False，于是整类人从逾期告警里静悄悄地掉了出去。上一版需求文档 5.1 节写清了两条路径，7.6 节却只给出了一条路径的逾期定义——两条路径是知道的，只是没人把它们和告警口径对上。

2.4 一本证的四种去向（单位统一为「本」）

术语定义（判据函数）不是什么
在库 在控人员台账上登记、且号码不在当前借出集合里的每一本证。certificate.stock_split() 的第一个返回值。 不是「没有出国申请的人数」。它是可以拿去和柜子里的实体证逐本核对的那个数。
借出未还 号码出现在 cert_issuance 中 status='issued' 的记录里。certificate.lent_out_numbers()。 不等于逾期。刚借出去、还没到归还期限的，就在这一档里，完全正常。
新办未入库 路径 B：做证的申请中，新证号码尚未进入证照台账的。travel.new_making_travel_ids()。 不等于逾期，也不在「在库 + 借出未还」里——这本证存在于现实，却还没进过台账、也没进过柜子，必须单独成一档。
逾期未交回 路径 A 与路径 B 合并，且 今天 > 到期日。travel._overdue_ids()。 不是一个独立的「第四堆证」——它是前两档中超了时限的那部分，会与它们重复计数。所以是 ⊆ 而不是 +。
两个必须永远成立的恒等式（第 10 章展开）：
① 在库 + 借出未还 = 在控人员台账登记的总本数　（相加式，全等）
② 逾期 ⊆ 借出未还 ∪ 新办未入库　（包含式，不是相加）

术语定义

3、用户角色

这一节怎么填
回答什么问题
谁会坐在这个系统前面，他一天里的动作序列是什么。
不写的代价
不写角色，「首页放什么」就没有依据。本项目首页曾经堆着分布统计、到期预警、本月领用数、逾期明细——每一张卡单看都「有信息量」，合起来却没有一张能让经办人知道今天该干什么。后来按「经办人打开首页要回答的三个问题」重排，删掉三张、重做四张，才收敛。角色定义就是首页取舍的裁判。
怎么填
角色数量少不是省略的理由——一个角色也要写，因为要写的是他的动作序列和判断依据，不是权限矩阵。如果确实只有一个角色，就明确写「不做权限体系」（呼应 1.4），免得后人替你「补全」。

3.1 角色清单

本系统只有一个角色：证照保管处经办人。

users 表结构为 id / username / password_hash / full_name / created_at，不含 role 列，代码中也不存在任何按角色分支的逻辑。所有登录者能做的事完全相同。

full_name 不参与鉴权，它的用途是：单据与操作日志上的「经办人」署名（helpers.operator_name()）。

3.2 经办人的典型动作序列

场景触发动作序列
每天开机打开首页 看四张证件去向卡 → 若「逾期未交回」不为 0，点进出国明细的 ?passport_status=overdue 筛选 → 逐个打电话催 → 若有孤儿号码告警，去查数据。
新人入册人事送来材料 信息登记表 → 人员备案 → 收缴证件、证照台账登记（填号码 + 有效期 + 上交日期）。
有人要出国收到申请表 建出国申请 → 上传附件 → 分路径：证在库的走「证件领用登记」（本人手写签名）；需做新证的标 need_new_passport='是'，本人自己去公安办。
有人回国本人来交证 路径 A：在领用单上办「归还登记」（本人手写签名）；路径 B：把新证号码补录进证照台账并填上交日期——这一步同时就是「已交回」的判据，做完逾期告警自动消失。
行程黄了本人告知不去了 在出国申请上「取消行程」（记取消日期）→ 到期日自动改为取消日 + 5 个工作日 → 催证。不要删除申请，删不掉也不该删（见 9.1）。
有人调走人事通知 先把证清干净（归还 / 交回入库）→ 发起撤控，填证件移交日期（必填）→ 该人退出所有告警口径与盘库清单。
定期盘库季度 / 年度 打开「证件盘库清单」→ 打印「应在库」表 → 打开柜子逐本打勾 → 对不上的去「借出未还」表和孤儿号码告警里找。

3.3 首页只回答三个问题

  1. 柜子里现在应该有多少本证？（在库，可直接与实体核对）
  2. 有多少本证不在柜子里，分别是什么情况？（借出未还 / 新办未入库）
  3. 其中有多少本该回来而没回来？（逾期未交回，可点进明细）

不能归入这三问之一的，一律不上首页。这条规则直接删掉了「本月证件领用数」（是回顾，不是待办）、「证照到期预警」（证只有出国申请才能领出去换发，没有申请时到期也只能在库放着，看了也不能行动）、以及三项分布统计。

4、实体关系图

这一节怎么填
回答什么问题
这些表是怎么连起来的——以及同样重要的：哪些连接数据库根本不知道。
不写的代价
本项目真正伤人的连接，一条外键都没有：
· 配置表被业务表按名字的文字引用（certificates.unit = '总部'）——改名与删除都是静默破坏，第 5 批返工三处；
· 证照台账与出行、领用之间靠证件号码字符串相等联系——删一条台账会让一条出行当场变回逾期，第 4 批返工。
只画外键的 ER 图会把这两类连接全部隐藏，而它们恰恰是出事最多的地方。图上不画出来，评审时就没人会问「改了这个名字，谁会跟着坏」。
怎么填
用三种线型区分三种引用强度：数据库强制的外键、靠文字相等的软引用、靠业务编号相等的软引用。后两种在别的项目里也许叫别的名字，但只要存在「A 表存的是 B 表某个值的副本」，就必须有一根线。
验收标准：图上每一根非外键的线，都能在第 8 章的矩阵里找到对应的守卫或同步动作；找不到的，就是一个还没被发现的返工。

4.2 三种引用强度

强度连接方式数据库知道吗破坏方式与防线
外键引用整数 id知道，且强制 直接 DELETE 会因外键约束静默失败，所以删除入口一律先查引用数再给明确提示（personnel.delete 查四张表）。
文字引用名字的文字副本完全不知道 删掉配置项 → 历史记录里的名字变成下拉里再也选不到的孤儿值；改名 → 同一项在统计里裂成两个。防线是 utils/textref.py：count_refs / describe_refs / sync_refs / backup_before_bulk_edit。
号码比对证件号码字符串相等完全不知道 删一条台账 → 引用它号码的出行当场变回「逾期未交回」（路径B 判据就是「号码在不在台账里」）。防线是 certificate._cert_references()，三个号码槽逐个查 travel_details.passport_no 与 cert_issuance.cert_nos。

5、业务模块与字段表

这一节怎么填
回答什么问题
每一列是谁写的、什么时候写的、别处变了它跟不跟着变。不是「这一列叫什么」——那看表结构就够了。
不写的代价
本项目所有字段级的返工，错的都不是类型或是否必填，而是这一列的**性质**没写清：
· certificates.name/unit/department 是台账（该跟人走），却和 cert_issuance 里的同名列被当成一回事，人员改名后台账不同步——第 6 批返工；
· travel_details.passport_no/passport_collect_date/passport_return_date 早期是手填的，与领用记录各写各的，打印件上「证件号码」和「证件领用日期」可能来自不同的证——后来降级为派生并把界面改成只读；
· decontrol_filing.cert_handover_date 在上一版需求文档里写着「选填」，实际上撤控以证件收缴完毕为前提，它是这件事发生过的凭据，必须必填。
一句「选填」写错，撬动的是整条业务规则。
怎么填
每一列打一个性质标签，只有五种：录入用户填；派生由别处回算写入（界面必须只读，并标注唯一写入方）；定格建单时复制一份此后永不同步；跟人走台账列，源头变了要同步；系统主键、时间戳、经办人。
填法上有一条硬要求：对着数据库实际的表结构逐列核，不要照抄上一版文档。本文这一节是用 PRAGMA table_info 把 12 张表全部导出后逐行核对写的，因此列数、可空性、默认值都与运行中的库一致。
另外要专门标出「schema 比业务宽松」的列（本项目有一处：cert_issuance.travel_id 列上可空、业务上必填），否则读表结构的人一定会误判。

性质标签： 录入 用户在表单里填   派生 由别处回算写入，界面只读   定格 建单时复制，此后永不同步   跟人走 台账列，源头变了要同步   系统 主键 / 时间戳 / 经办人

日期格式：所有业务日期列都是 TEXT，格式 YYYYMMDD（如 20260301）。只有 created_at / updated_at / uploaded_at 是 TIMESTAMP。用文本存日期是有意的：全系统按字符串比较大小即为按日期比较，且导入导出与打印都不必转换。

9.2 为什么撤销撤控是物理删除

撤销撤控没有把记录标成「已作废」，而是物理删除那条 decontrol_filing。理由是撤控表是报出去的备案单据，一条记录的含义就是「这个人已上报撤控」。撤销意味着这件事没有发生过——留一条作废的单据反而会在列表和导出里制造「他到底撤没撤」的歧义。

物理删除的前提是留痕留得住：删除前写入完整的 before 快照（log_action('delete', 'decontrol_filing', id, before=…)），撤控原因、报送单位、入库批号这些只此一份的信息全部在快照里。需要追溯时查日志——这正是操作日志该干的事。测试 test_revoke_logs_full_snapshot 逐个断言这三项信息在快照里查得回来。

另一处细节：状态回滚写的是 WHERE id = ? AND status = 'decontrolled'，并检查 rowcount。人员备案可能已被删除（撤控单自带姓名与身份证快照，不依赖它存在），这时提示会明说「未找到对应的有效备案人员，请到人员备案确认其状态」，而不是假装成功。

11.4 一处例外：撤控入口不置灰

为什么不像「证件领用登记」那样置灰：清障状态要查两张表才知道（_unsettled_certs() 查 cert_issuance 与 travel_details），而人员列表一页几百行，逐行判断代价不成比例；更重要的是，置灰只能显示一行 tooltip，说不清「还差哪几样」，而这里恰恰需要说清楚。

但有一条底线守住了：拦截放在 GET 上，而不是等人填完一整张撤控表再报错。代码注释：「让人填完一整张表再告诉他不行，是最没必要的一种为难。」

12、提示文案规约

这一节怎么填
回答什么问题
系统拒绝一个操作时，该说什么。
不写的代价
本项目出过一条照做也没用的提示。删除出国申请被挡下时，提示写的是「请先作废相关领用记录」——用户照做，去把领用记录一条条作废，回来再删，还是被挡。因为守卫压根不看 status，作废的照样算数。
而这不是判据写漏了：领用单上有本人手写签名，作废是「这次领用作废」，不是「这次领用没发生过」，单子仍要留档、仍然指着这条出行。判据是对的，错的是那句话。
这类错误比功能 bug 更伤人：它让人白干一遍活，还让人怀疑系统坏了。而它在任何测试里都不会红——断言「返回 200 且被挡下」照样通过。
怎么填
把系统里所有拒绝类提示抄出来，逐条问三个问题：
① 说清挡在哪一条上了吗？（最好带数量明细，让人能自己核对）
② 指出的那条路走得通吗？——照着做一遍。这一步是唯一能抓到「作废重试还是被挡」那类错误的办法，测试抓不到。
③ 如果这条路本来就不该走，有没有告诉他该走哪条？

12.1 六条规约

规约一：提示必须指向一条走得通的路。 挡下之后要么给出可执行的下一步，要么明说「这件事做不了，请改用 X」。验收方式只有一个：照着提示做一遍。
规约二：说清挡在哪一条上，并给出数量明细。 「有关联记录，不能删除」不合格；要写「证照 2 条、出国明细 5 条、撤控记录 1 条、证件领用 3 条」——用户拿这个数字能自己去核对，也能判断是不是自己想的那些。
规约三：批量重写历史必须点名快照文件。 改名同步一次改掉几百条记录且没有 undo，所以成功提示里要写出快照文件名和还原方式，而不是一句「同步成功」。
规约四：不能假装成功。 部分成功就说部分成功。撤销撤控时如果人员备案已被删除、状态没能回滚，提示要明说「未找到对应的有效备案人员，请到「人员备案」确认其状态」，而不是统一报「已撤销」。
规约五：空值不能是空格子。 打印件与列表上的空格子，看的人分不清是「没有这个东西」还是「漏填了」。所以证件种类判不出来时显示「待核实」，未领用的日期显示「未领用」，没有数据的表格显示「暂无出国申请记录」。
规约六：数字要带单位。 凡是可数的，标签里就带上「（本）」「（人）」「（条）」。这条看着琐碎，但它是第 10 章那一整轮返工唯一的低成本预防手段。

13、导出 / 打印 / 查询 / 导入 / 日志 / 备份

这一节怎么填
回答什么问题
这些「每个模块都有一份」的功能，各自的口径是什么。
不写的代价
通用功能最容易被写成一句「支持导出 Excel」就过去了，然后每个模块各实现一遍，口径各不相同。本项目踩到的是「页面上看到的」和「导出出来的」不一致——盘库清单页做了筛选，导出如果自己重新查一遍库，两份东西就对不上，而拿去核对实体的正是导出那一份。
现在的做法是：数据由页面算好后传进导出函数，导出不重新查（export_cert_stock(operator, in_stock, lent_out)），并有两条测试钉住「导出与页面同源」「导出遵守筛选」。
怎么填
对每一项通用功能写清三样：覆盖哪些模块 / 数据从哪儿来 / 有没有保留期。
「数据从哪儿来」是关键：凡是页面上有筛选的，导出必须与页面同源，否则迟早对不上。
「保留期」也别漏——导出文件和备份文件都是只增不减的，而且都含敏感数据。

本项目为此炸过三次 CI，而且规则是被一次次撑大的：
①产品代码 Path.write_text() 写中文没给 encoding=；
②一周后，测试代码同样的写法——于是定下「读写文本文件必须显式 encoding」；

14.5 五版并行的约束

同一套业务由 5 种语言各实现一遍：Python 是源头，另有 Go / Rust / .NET / Java 四版（potms-go / potms-rust / potms-dotnet / potms-java）。五版共享同一个 data.db。

由此产生两条硬约束：

  • schema 只有一个源头。database.py 生成 .NET 与 Java 两版的 schema 文件，CI 用 gen-schema.py --check / gen-schema-java.py --check 守着，改了不同步就构建失败。
  • 任何一版的破坏，其余四版都要承受。因为共享一个库——一版能删掉被引用的证照、能带证撤控，另外四版就都得面对这个坏数据。这是第 15 章那条最高优先级欠账的全部理由。

CI 共 6 个工作流：五版各一个构建 + 一个 release.yml（五版一次出齐）。

#检查项为什么
1每个新测试都验证过「撤掉修复会变红」吗？而且要朝一个合理的错误方向改，不是整块删掉。 整块删掉往往会让别的断言先炸，看起来红了，其实没验证到这条。这是本项目最有价值的一条实践。
2造的数据能分辨出对错吗？断言写对了不等于测到了。 ⊆ 的用例里如果数据恰好相等，写成 = 也全绿。本项目补了一个「还没到期的新办」样本才让它变成真子集。
3断言的范围够窄吗？别拿整页 HTML 断言「不包含某人」。姓名在页面上到处都是（近期出行、表格行本身），整页断言既会误报也会漏报。
4用了秒级精度的字段做「有没有改动」的判断吗？updated_at 是秒级的，同一秒内的两次写入分辨不出来——本项目为此写坏过一个测试。改用 flash 文本或日志条数断言。
5同一个判据是不是只有一个实现？页面高亮、筛选、首页数字、导出，四处必须共用一个函数。已撤控人员的排除当初差点只加在筛选那一侧。
6改了一处之后，问过「还有哪里也是这样」吗？同一个编码根因在一周内咬了两次；同一批修复目前还在四个实现里等着（见 15.3 第一条）。
7所有读写文本文件的地方都写了 encoding="utf-8" 吗？Windows CI 用 cp1252，本地全绿、CI 炸掉。
8改了 schema 就重新生成了 .NET / Java 两份吗？CI 有 --check 守着，但本地先跑一遍省一轮往返。
9真的打开浏览器看过吗？测试全绿不等于界面对。 「首页有两张卡都叫证照逾期未还」「单位不一致」「新办 ≠ 逾期」——这三处连续被人眼发现，没有一处是测试或自审发现的。
10动过没有纳入版本控制的文件吗？改之前先备份。本项目在一次「撤掉修复看会不会红」的实验里损坏过一个未跟踪的模板文件，git checkout 救不回来。
11本文档跟着改了吗？文档落后于代码就等于错。上一版需求文档正是这么烂掉的。

15.3 已知欠账

优先级欠什么影响
高 第 4–6 批、仪表盘四档改造、以及本轮问题复核的三批修复，都只做了 Python 版，Go / Rust / .NET / Java 尚未同步 四版目前仍可能删掉被引用的证照、带证撤控、把路径 B 漏出告警。而五版共享同一个 data.db——从任何一版做出的破坏，其余四版都要承受。这是「修好一个 bug 不等于消除这一类 bug」在项目层面的翻版。
新增 本轮第 2 批给身份证号加了库层唯一索引。索引是库的属性，对五版一视同仁：这是好事（约束不再依赖哪一版在写），但另外四版的编辑路径若仍不查重，撞号时拿到的是一个 IntegrityError，多半直接 500，而不是一句能看懂的提示。
中release.yml（425 行，五版一次出齐）从来没有真正跑过一次 真到发版那天才第一次跑，是最不该冒的险。应当先拿一个测试 tag 空跑一遍。
中仓库里没有约定文档（CLAUDE.md / CONTRIBUTING.md） 「Python 为源头」「schema 改了要重新生成两份」「新测试必须验证会红」这些规矩全靠口头传，换人就断。本文的第 0 章与第 15 章接住了一部分，但工程约定仍然没有落纸。
中盘库只能出清单，盘点结果回不到系统 现在能打印一张带勾选框的清单、逐本划勾，但划完的那张纸没有入口回到系统。查不到「上次什么时候盘的、应到多少、实到多少、缺哪几本、谁盘的」。「盘库」目前实为「打印一张单子」。
低系统内没有「从备份恢复」的入口 真出事时操作员要停服、找文件、改文件名（README 三步），容易再出错。
低Go 与 Python 版没有版本号字符串 拿到一个 exe 无法判断是哪次构建的。
